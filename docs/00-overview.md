# 00 — Overview

> **TaskFlow Pro** — 팀 업무 관리 풀스택 웹앱

---

## 문서 매핑표

| 파일명 | 역할 | 알 수 있는 것 |
|--------|------|--------------|
| `00-overview.md` | 문서 지도 | 전체 문서 구조, 읽는 순서, 분리 이유 |

## 읽는 순서

```
00-overview  →  01-product  →  02-specs  →  03-design  →  04-tasks  →  05-conventions
   (지도)          (무엇을)       (어떻게)      (구조)        (순서)          (규칙)
```

새 작업을 시작할 때마다 이 순서대로 읽는다.
맥락 없이 코드를 작성하면 잘못된 가정이 누적되어 유지보수 비용이 급격히 증가한다.

---

## 왜 이렇게 나누는가 — 관심사 분리(Separation of Concerns) 원칙

하나의 문서에 모든 정보를 몰아넣으면 세 가지 문제가 생긴다.

1. **변경 충돌**: 기능 요구사항이 바뀔 때 기술 명세까지 같은 파일을 건드려야 한다.
2. **맥락 오염**: "무엇을 만드는가"와 "어떻게 만드는가"가 섞이면 의사결정 근거를 추적하기 어렵다.
3. **탐색 비용**: 규칙을 확인하러 들어왔다가 DB 스키마를 읽어야 하는 상황이 발생한다.

각 문서는 **단 하나의 질문에만 답한다.**

| 문서 | 답하는 질문 |
|------|------------|
| `01-product` | 무엇을 만드는가? (What) |
| `02-specs` | 어떤 기술로 만드는가? (How — Tech) |
| `03-design` | 어떤 구조로 만드는가? (How — Structure) |
| `04-tasks` | 어떤 순서로 만드는가? (When) |
| `05-conventions` | 어떤 규칙을 지키는가? (Rules) |

이 원칙을 지키면 한 문서를 수정해도 다른 문서에 파급 효과가 없고,
새 팀원이 필요한 맥락만 골라 읽을 수 있다.
